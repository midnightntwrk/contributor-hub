# Building a Commit/Reveal Voting System in Compact

A comprehensive tutorial on building a privacy-preserving DAO voting contract for the Midnight Network.

## Introduction

Decentralized voting systems face a fundamental tension: how do you verify eligibility without revealing identity? How do you prevent double-voting without maintaining a centralized registry? The commit/reveal pattern, combined with Midnight's cryptographic primitives, provides an elegant solution.

This tutorial walks you through building a complete voting system with:

- **Commit Phase**: Voters submit a hash of their vote + secret salt
- **Reveal Phase**: Voters reveal their vote, which is verified against the commitment
- **Nullifiers**: Prevent double-voting while maintaining anonymity
- **Merkle Tree**: Verify voter eligibility without exposing voter list
- **Time-Locked Phases**: Enforce voting windows using block time

## Why Commit/Reveal?

Traditional on-chain voting has a problem: votes are visible immediately. This enables:

1. **Vote Buying**: Someone can pay you to vote a certain way, then verify on-chain
2. **Coercion**: An attacker forces you to reveal your vote under threat
3. **Front-Running**: Bots see your vote and react before it's finalized

The commit/reveal pattern solves this by separating voting into two phases:

1. **Commit Phase**: Submit `Hash(vote, random_salt)` — no one can decode this
2. **Reveal Phase**: Submit `(vote, salt)` — contract verifies it matches

At the end of commit phase, the secret is revealed — but by then, votes have been locked.

## Core Concepts

### The Commit/Reveal Pattern

The commit/reveal pattern separates voting into two phases:

1. **Commit Phase**: Voter submits `Hash(vote, secret)` — the vote is hidden
2. **Reveal Phase**: Voter reveals `(vote, secret)` — the contract verifies it matches

This prevents vote buying and coercion since neither the voter nor anyone else can prove how they voted until after the commit phase closes.

The key insight is that the hash function is one-way: given `Hash(vote, salt)`, it's computationally infeasible to recover either `vote` or `salt`. This keeps votes private until the reveal phase.

### Nullifiers and Double-Vote Prevention

A nullifier is a unique identifier derived from the voter's secret that:

- Can only be generated by the voter (using their secret key)
- Is inserted into a public Set after revealing
- Cannot be used twice

The nullifier is separate from the commitment. Here's why:

1. ** voter commits**: `Commitment = Hash(vote, secret, salt)`
2. **Voter reveals**: Compute `Nullifier = Hash(secret)` — different hash!
3. **Contract checks**: Nullifier not in Set → allow vote, then insert

This way, even if someone sees your commitment, they can't produce a valid nullifier to double-vote.

### Domain Separation

Using `persistentCommit` with different domain separators ensures:

- Commitment hash ≠ Nullifier hash (even with same inputs)
- Prevents cross-protocol attacks

The domain separator is a constant string that distinguishes different cryptographic uses:

```compact
circuit computeCommitment(vote: VoteOption, sk: Bytes<32>, salt: Bytes<32>): Bytes<32> {
  const domainSep = pad(32, "midnight:voting:commitment");
  return persistentCommit<Vector<3, Bytes<32>>>([domainSep, vote as Bytes<32>, sk], salt);
}

circuit computeNullifier(sk: Bytes<32>): Bytes<32> {
  const domainSep = pad(32, "midnight:voting:nullifier");
  return persistentCommit<Vector<2, Bytes<32>>>([domainSep, sk], pad(32, "nullifier-salt"));
}
```

Notice the different domain strings: "midnight:voting:commitment" vs "midnight:voting:nullifier"

### Merkle Trees for Anonymous Eligibility

A common requirement is: "only eligible voters can vote" — but how do you prove eligibility without revealing who you are?

The solution: Merkle trees. The contract stores a Merkle root of all eligible voters. Each voter proves membership by providing a path (without revealing their identity):

```compact
export ledger eligibleVoters: MerkleTree<20, Bytes<32>>;
export circuit verifyEligible(voterPk: Bytes<32>): [] {
  const path = findVoterPath(voterPk);
  const root = merkleTreePathRoot<20, Bytes<32>>(path);
  assert(eligibleVoters.checkRoot(root), "not eligible");
}
```

The `findVoterPath` witness provides the proof. The contract verifies the root. The public never learns which voter proved eligibility — only that someone did.

### Time-Locked Phases

Midnight contracts can enforce time using block time primitives:

- `blockTimeLt(time)`: Current time < time
- `blockTimeGte(time)`: Current time >= time

This ensures phases have fixed durations:

```compact
export circuit startCommitPhase(commitDuration: Uint<64>): [] {
  assert(organizer == ownPublicKey(), "not authorized");
  assert(phase == VotingPhase.INIT, "wrong phase");
  phase = VotingPhase.COMMIT;
  phaseDeadline = commitDuration;
}

export circuit startRevealPhase(revealDuration: Uint<64>): [] {
  assert(organizer == ownPublicKey(), "not authorized");
  assert(phase == VotingPhase.COMMIT, "not in commit phase");
  assert(blockTimeGte(phaseDeadline), "deadline not reached");
  phase = VotingPhase.REVEAL;
  phaseDeadline = blockTimeLt(0) as Uint<64> + revealDuration;
}
```

## The Contract

Here's our complete voting contract:

```compact
pragma language_version 0.22;

import CompactStandardLibrary;

export enum VotingPhase {
  INIT,
  COMMIT,
  REVEAL,
  ENDED
}

export enum VoteOption {
  ABSTAIN,
  YES,
  NO
}

export ledger organizer: ZswapCoinPublicKey;
export ledger proposalTitle: Bytes<64>;
export ledger proposalDescription: Bytes<256>;
export ledger phase: VotingPhase;
export ledger phaseDeadline: Uint<64>;

export ledger eligibleVoters: MerkleTree<20, Bytes<32>>;
export ledger voterCommitments: Map<Bytes<32>, Bytes<32>>;
export ledger voterNullifiers: Set<Bytes<32>>;

export ledger yesVotes: Counter;
export ledger noVotes: Counter;
export ledger abstainVotes: Counter;
export ledger totalCommitted: Counter;
export ledger totalRevealed: Counter;
```

### Understanding the State

Let's break down what each piece of state does:

**Proposal Metadata:**

- `organizer`: The public key that controls the voting (can change phases)
- `proposalTitle`: Up to 64 bytes for the proposal name
- `proposalDescription`: Up to 256 bytes for details
- `phase`: Current voting phase (INIT, COMMIT, REVEAL, ENDED)
- `phaseDeadline`: Block time when current phase ends

**Voter Management:**

- `eligibleVoters`: Merkle tree of all allowed voters (depth 20 = ~1M capacity)
- `voterCommitments`: Map from voter public key → their commitment hash
- `voterNullifiers`: Set of used nullifiers (prevents double-vote)

**Vote Tallying:**

- `yesVotes`: Counter for YES votes
- `noVotes`: Counter for NO votes
- `abstainVotes`: Counter for abstentions
- `totalCommitted`: How many committed (regardless of reveal)
- `totalRevealed`: How many revealed (and counted)

### Constructor

```compact
constructor(
  title: Bytes<64>,
  description: Bytes<256>,
  commitDuration: Uint<64>,
  revealDuration: Uint<64>,
  sk: Bytes<32>
) {
  organizer = ownPublicKey();
  proposalTitle = disclose(title);
  proposalDescription = disclose(description);
  phase = VotingPhase.INIT;
  phaseDeadline = commitDuration + revealDuration;
}
```

The constructor:

1. Sets the organizer to the deployer's public key
2. Stores the proposal metadata (using `disclose` to make it public)
3. Sets initial phase to INIT
4. Calculates total deadline (for reference)

### Phase Transitions

```compact
export circuit startCommitPhase(commitDuration: Uint<64>): [] {
  assert(organizer == ownPublicKey(), "not authorized");
  assert(phase == VotingPhase.INIT, "wrong phase");
  phase = VotingPhase.COMMIT;
  phaseDeadline = commitDuration;
}

export circuit startRevealPhase(revealDuration: Uint<64>): [] {
  assert(organizer == ownPublicKey(), "not authorized");
  assert(phase == VotingPhase.COMMIT, "not in commit phase");
  assert(blockTimeGte(phaseDeadline), "deadline not reached");
  phase = VotingPhase.REVEAL;
  phaseDeadline = blockTimeLt(0) as Uint<64> + revealDuration;
}

export circuit endVoting(): [] {
  assert(organizer == ownPublicKey(), "not authorized");
  assert(phase == VotingPhase.REVEAL, "not in reveal phase");
  assert(blockTimeGte(phaseDeadline), "deadline not reached");
  phase = VotingPhase.ENDED;
}
```

Each transition:

1. Verifies the caller is the organizer
2. Verifies we're in the correct phase
3. Verifies the deadline has passed (for COMMIT→REVEAL and REVEAL→ENDED)
4. Updates to the next phase

### Adding Eligible Voters

```compact
export circuit addEligibleVoters(voterPk: Bytes<32>): [] {
  assert(organizer == ownPublicKey(), "not authorized");
  eligibleVoters.insert(voterPk);
}

export circuit verifyEligible(voterPk: Bytes<32>): [] {
  const path = findVoterPath(voterPk);
  const root = merkleTreePathRoot<20, Bytes<32>>(path);
  assert(eligibleVoters.checkRoot(root), "not eligible");
}
```

The organizer can add voters to the Merkle tree. When a voter wants to vote, they use the witness to prove membership — the path is never disclosed publicly.

**Note**: The depth-20 Merkle tree supports ~1 million voters. Adjust as needed for your DAO.

### The Commit Circuit

```compact
export circuit commitVote(voterPk: Bytes<32>): [] {
  assert(phase == VotingPhase.COMMIT, "not in commit phase");
  assert(blockTimeLt(phaseDeadline), "commit deadline passed");

  const sk = localSecret();
  const dVoterPk = disclose(voterPk);
  verifyEligible(dVoterPk);

  const salt = localSalt();
  const vote = localVote();
  assert(vote != VoteOption.ABSTAIN, "cannot commit abstain");

  const commitment = computeCommitment(vote, sk, salt);
  assert(!voterCommitments.member(dVoterPk), "already committed");

  voterCommitments.insert(dVoterPk, commitment);
  totalCommitted.increment(1);
}
```

The commit flow:

1. Check we're in commit phase and before deadline
2. Get voter's secret from local witness
3. Verify voter is eligible (via Merkle proof)
4. Get vote and random salt from local witness
5. Compute commitment hash
6. Check voter hasn't already committed
7. Store commitment in Map
8. Increment committed counter

### The Reveal Circuit

```compact
export circuit revealVote(voterPk: Bytes<32>): [] {
  assert(phase == VotingPhase.REVEAL, "not in reveal phase");
  assert(blockTimeLt(phaseDeadline), "reveal deadline passed");

  const sk = localSecret();
  const dVoterPk = disclose(voterPk);
  verifyEligible(dVoterPk);

  const storedCommitment = voterCommitments.lookup(dVoterPk);
  assert(storedCommitment != none, "not committed");

  const salt = localSalt();
  const vote = localVote();
  assert(vote != VoteOption.ABSTAIN, "cannot reveal abstain");

  const nullifier = computeNullifier(sk);
  assert(!voterNullifiers.member(nullifier), "already revealed");
  voterNullifiers.insert(disclose(nullifier));

  const commitment = computeCommitment(vote, sk, salt);
  assert(storedCommitment == commitment, "commitment mismatch");

  if (disclose(vote) == VoteOption.YES) {
    yesVotes.increment(1);
  } else {
    noVotes.increment(1);
  }
  totalRevealed.increment(1);
}
```

The reveal flow:

1. Check we're in reveal phase and before deadline
2. Verify eligibility (Merkle proof)
3. Look up stored commitment (must have committed)
4. Get vote and salt from witness
5. Compute nullifier, check not used (prevents double-vote)
6. Insert nullifier to Set
7. Recompute commitment, verify matches stored
8. Increment appropriate vote counter

### Commitment and Nullifier Computation

```compact
circuit computeCommitment(vote: VoteOption, sk: Bytes<32>, salt: Bytes<32>): Bytes<32> {
  const domainSep = pad(32, "midnight:voting:commitment");
  return persistentCommit<Vector<3, Bytes<32>>([domainSep, vote as Bytes<32>, sk], salt);
}

circuit computeNullifier(sk: Bytes<32>): Bytes<32> {
  const domainSep = pad(32, "midnight:voting:nullifier");
  return persistentCommit<Vector<2, Bytes<32>>([domainSep, sk], pad(32, "nullifier-salt"));
}
```

These circuits:

1. Use `persistentCommit`: A commitment primitive that persists across upgrades
2. Apply domain separation: Different strings for different purposes
3. Include randomness (salt for commitment, fixed salt for nullifier)

The domain separation is critical: Without it, an attacker could try to use the same key material for both commitment and nullifier, potentially linking votes.

## TypeScript Integration

Here's how to interact with the contract from TypeScript:

```typescript
import {
  createVotingContract,
  computeCommitment,
  computeNullifier,
  VotingPhase,
  VoteOption,
  type VotingConfig,
} from "./voting-contract";

// Initialize the contract
const config: VotingConfig = {
  title: " Governance Proposal #1",
  description: "Should we upgrade the protocol?",
  commitDuration: 86400n,    // 24 hours
  revealDuration: 86400n,  // 24 hours
  secretKey: generateSecretKey(),
};

const contract = createVotingContract(config);

// For a voting session:
function generateSecretKey(): Uint8Array {
  return crypto.getRandomValues(new Uint8Array(32));
}

function generateRandomSalt(): Uint8Array {
  return crypto.getRandomValues(new Uint8Array(32));
}

// Phase 1: Commit your vote
const mySecret = generateSecretKey();
const mySalt = generateRandomSalt();
const myVote = VoteOption.YES;
const commitment = computeCommitment(myVote, mySecret, mySalt);

// Submit commitment to contract
await contract.commitVote(myPublicKey, commitment);

// Phase 2: Reveal your vote
await contract.revealVote(myPublicKey, myVote, mySecret, mySalt);
```

## Security Properties

### What the Contract Provides

1. **Vote Privacy**: No one can see your vote during the commit phase — they only see a hash
2. **Double-Vote Prevention**: Nullifiers prevent voting twice, even if you commit twice
3. **Eligibility Verification**: Merkle proof keeps voter list private from the public
4. **Time Enforcement**: Block time ensures phases have fixed durations
5. **Domain Separation**: Commitment ≠ Nullifier (different derivation paths)

### What It Doesn't Provide

This contract doesn't provide:

- **Receipt-freeness**: A voter can prove how they voted to a coercer
- **Individual verifiability**: You can't verify your specific vote was counted
- **Tally correctness**: Requires trust in the reveal phase integrity

For production systems, consider adding:

- **Blind signatures** for receipt-freeness
- **Verifiable shuffling** for tally verifiability
- **Multi-party computation** for tally aggregation
- **Encrypted tally** that only reveals after all reveal

## Complete Workflow

Here's the full voting workflow:

```
1. DEPLOY
   - Organizer deploys contract with proposal metadata
   - Contract starts in INIT phase

2. ADD VOTERS
   - Organizer adds eligible voters to Merkle tree
   - Voters can verify eligibility privately

3. START COMMIT PHASE
   - Organizer calls startCommitPhase()
   - Commit deadline is set
   - Voters can now commit

4. COMMIT
   - Each voter:
     a. Generates random salt
     b. Computes: commitment = Hash(vote, sk, salt)
     c. Calls commitVote(commitment)
   - No one sees the actual vote

5. START REVEAL PHASE
   - After commit deadline passes
   - Organizer calls startRevealPhase()
   - Reveal deadline is set
   - Voters now reveal

6. REVEAL
   - Each voter:
     a. Reveals: (vote, secret, salt)
     b. Contract verifies against stored commitment
     c. Contract inserts nullifier to prevent re-use
     d. Vote is counted
   - If commitment doesn't match → reveal fails

7. END VOTING
   - After reveal deadline passes
   - Organizer calls endVoting()
   - Results are finalized

8. GET RESULTS
   - Anyone can read yesVotes, noVotes
   - Winner is determined
```

You get a complete voting system that respects voter privacy while maintaining on-chain integrity.

## Real-World Example: DAO Proposal

Let's walk through a real scenario:

**The Setup:**

A DAO has 1,000 members. They want to vote on upgrading the protocol. The DAO administrator:

1. Deploys the contract with:
   - Title: "Protocol Upgrade Proposal #7"
   - Description: "Upgrade to v2.0 with privacy enhancements"
   - Commit duration: 3 days (259,200 seconds)
   - Reveal duration: 2 days (172,800 seconds)

2. Adds all 1,000 members to the Merkle tree

3. Starts the commit phase

**The Voting:**

Member Alice wants to vote YES:

1. She generates:
   - Secret key: `0x1a2b3c...` (her wallet key)
   - Salt: Random 32 bytes

2. She computes:
   ```
   commitment = Hash("midnight:voting:commitment" + YES + secret, salt)
   ```

3. She submits the commitment during commit phase

She cannot reveal her vote during this phase. Even if someone asks "did you vote YES?", she can truthfully say "I committed, but I won't show you what."

**The Reveal:**

After commit phase ends, Alice reveals:

1. She provides: (YES, secret, salt)
2. Contract recomputes: commitment = Hash(...)
3. Matches stored commitment? Yes → count vote
4. Insert nullifier to prevent re-usage
5. YES counter increments

The contract guarantees:

- Alice voted (her commitment is on-chain)
- Alice can only vote once (nullifier check)
- Alice's vote is counted (matching commitment)

## Troubleshooting Common Issues

### "Not Eligible" Error

**Cause:** Your public key is not in the Merkle tree

**Solution:** Contact the organizer to add you before committing

### "Already Committed" Error

**Cause:** You already submitted a commitment

**Solution:** You cannot change your commitment. Wait for reveal phase to reveal your actual vote.

### "Commitment Mismatch" Error

**Cause:** The (vote, secret, salt) doesn't match your stored commitment

**Solution:** Make sure you're using the exact same values from commit phase

### "Deadline Not Reached" Error

**Cause:** Trying to transition phases before the deadline

**Solution:** Wait for the block time to pass the deadline

### "Not Authorized" Error

**Cause:** Trying to perform organizer action without organizer key

**Solution:** Use the correct wallet that deployed the contract

## Security Considerations

### Salt Generation

Always generate fresh salt for each vote:

```typescript
// BAD: Using predictable values
const salt = new Uint8Array(32).fill(0);

// GOOD: Using crypto
const salt = crypto.getRandomValues(new Uint8Array(32));
```

### Secret Key Handling

Never expose your secret key. Only share:

- Commitment (the hash)
- During reveal: vote + salt (but not secret key in plaintext)

### Front-Run Protection

The commit phase inherently prevents front-running since votes are hidden until reveal.
