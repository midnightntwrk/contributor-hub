# When Proofs Fail: Debugging Proof Server Errors & ZK Generation Failures on Midnight

## Introduction

Zero-knowledge proofs are at the heart of Midnight's privacy model. Every shielded transaction requires a ZK proof generated by the proof server. But when proofs fail, the errors can be cryptic — and without a working proof server, your contract interactions grind to a halt.

This tutorial covers every common proof failure mode, how to diagnose it, and how to fix it.

## Architecture Overview

The Midnight proof server is a standalone Docker service that generates ZK proofs from circuit inputs:

```
[Your dApp/Client] → [Circuit Witness Data] → [Proof Server (port 6300)] → [ZK Proof] → [Transaction]
```

The proof server is separate from the Midnight node. You can run it locally during development or connect to a remote instance.

## Failure Mode 1: Proof Server Not Responding

**Symptom:** Transactions hang at "generating proof..." and eventually time out.

**Root causes:**
- Docker container not running
- Port conflict or firewall blocking port 6300
- Proof server service crashed

### Diagnosis

```bash
# Check if the container is running
docker ps | grep proof-server

# Expected output: midnight-proof-server container should be UP

# Check container logs
docker logs midnight-proof-server --tail 50

# Check if the port is listening
curl -s -o /dev/null -w "%{http_code}" http://localhost:6300/health
# Expected: 200

# Or use netcat
nc -zv localhost 6300
```

### Resolution

```bash
# Restart the proof server
docker compose restart proof-server

# If the container isn't running
docker compose up -d proof-server

# Check Docker daemon is running
systemctl status docker
```

## Failure Mode 2: Proof Timeout

**Symptom:** The first proof generation takes 5-15 minutes; subsequent proofs are fast.

**Root causes:**
- First-time ZK parameter download (~30MB)
- Proof server is generating proving/verifying keys
- Under-resourced environment (CPU/memory)

### Why the first proof is slow

The first time you run a proof server, it needs to:

1. **Download ZK parameters** (~30MB) — these are the structured reference string (SRS) for your circuit's proving system. They're cached after the first download.
2. **Generate proving keys** — circuit-specific keys are derived from the SRS. This is CPU-intensive.
3. **Cache circuit artifacts** — compiled circuit data is cached in memory.

### Diagnosis

```bash
# Check if params are being downloaded
docker logs midnight-proof-server --tail 20 | grep -i "download\|param\|srs"

# Check CPU/memory usage during proof generation
docker stats midnight-proof-server --no-stream

# Check available disk space (needs ~1GB for cache)
df -h /var/lib/docker
```

### Resolution

```bash
# Option 1: Pre-download parameters (recommended)
# The proof server downloads automatically on first request.
# Just be patient for the first proof (~10 minutes).

# Option 2: Check parameter cache
docker exec midnight-proof-server ls -la /app/params/

# Option 3: Increase resource allocation
# Edit docker-compose.yml to add:
#   deploy:
#     resources:
#       limits:
#         cpus: '4'
#         memory: '8G'
```

**Production tip:** Pre-warm the proof server during deployment by generating a dummy proof before handling real traffic. This ensures the first real transaction doesn't experience the timeout.

## Failure Mode 3: Proof Rejection — Wire Format Mismatch

**Symptom:** The proof server returns a proof, but the node rejects it with "Invalid proof" or "Proof deserialization failed".

**Root causes:**
- Proof server and node are running different versions
- Wire format changed between releases
- Proof was generated for a different circuit than expected

### Diagnosis

```bash
# Check proof server version
docker exec midnight-proof-server /app/proof-server --version

# Check node version
midnight-node --version

# Compare against the compatibility matrix
# https://docs.midnight.network/relnotes/compatibility-matrix

# Look for version mismatch in node logs
docker logs midnight-node --tail 50 | grep -i "proof\|version\|mismatch"
```

### Resolution

```bash
# Step 1: Pull the correct proof server Docker image
# The tag MUST match your node version
docker pull midnightntwrk/proof-server:0.22.5

# Step 2: Update docker-compose.yml
#   image: midnightntwrk/proof-server:0.22.5

# Step 3: Recreate the container
docker compose down proof-server
docker compose up -d proof-server

# Step 4: Purge and regenerate proof cache
docker exec midnight-proof-server rm -rf /app/params/*
docker compose restart proof-server
```

## Failure Mode 4: Version Mismatch — Proof Server Docker Tag vs Ledger Version

**Symptom:** Consistent proof failures on all transactions after an upgrade.

**Root causes:**
- You upgraded your Midnight node but not the proof server
- The Docker image tag is pinned to an old version
- CI/CD pipeline deploys mismatched services

### The Version-Matching Rule

The proof server Docker image TAG must exactly match the **ledger component version**, not necessarily the node release version. Check the [compatibility matrix](https://docs.midnight.network/relnotes/compatibility-matrix) for the correct pairing.

### Diagnosis

Create a version inventory:

```bash
echo "=== Version Inventory ==="
echo "Proof Server: $(docker exec midnight-proof-server /app/proof-server --version 2>/dev/null || echo 'unknown')"
echo "Midnight Node: $(midnight-node --version 2>/dev/null || echo 'unknown')"
echo "Compact Compiler: $(compact --version 2>/dev/null || echo 'unknown')"

# Compare Docker image tag
docker inspect midnightntwrk/proof-server:$(docker inspect midnight-proof-server --format '{{.Config.Image}}' | cut -d: -f2)
```

### Resolution

```bash
# 1. Check what versions are compatible
#    Visit: https://docs.midnight.network/relnotes/compatibility-matrix

# 2. Update all services to the same compatible version
#    The safest approach is to update everything at once:
export MIDNIGHT_VERSION="0.22.5"

docker pull midnightntwrk/node:${MIDNIGHT_VERSION}
docker pull midnightntwrk/proof-server:${MIDNIGHT_VERSION}
docker pull midnightntwrk/indexer:${MIDNIGHT_VERSION}

docker compose down
docker compose up -d
```

## Failure Mode 5: Out of Memory / Resource Exhaustion

**Symptom:** Proof generation fails with "memory allocation failed" or the Docker container OOM-killed.

**Root causes:**
- Proof generation requires significant RAM (~4-8GB for complex circuits)
- Multiple concurrent proof generations exhausting available memory
- Docker memory limits set too low

### Diagnosis

```bash
# Check if container was OOM-killed
docker inspect midnight-proof-server --format='{{.State.OOMKilled}}'
# Returns: true if OOM-killed

# Check resource limits
docker inspect midnight-proof-server --format='{{.HostConfig.Memory}}'
# 0 = unlimited, otherwise shows bytes

# Monitor memory usage during proof generation
docker stats midnight-proof-server
```

### Resolution

```bash
# Option 1: Increase Docker memory limit
# Edit ~/.docker/config.json or set in docker-compose.yml:
#   deploy:
#     resources:
#       limits:
#         memory: 8G

# Option 2: Reduce concurrent proofs
# Serialize proof requests in your dApp — don't submit multiple at once

# Option 3: Add swap space
fallocate -l 8G /swapfile
chmod 600 /swapfile
mkswap /swapfile
swapon /swapfile

# Make permanent in /etc/fstab:
# /swapfile swap swap defaults 0 0
```

## How to Verify Proof Server Health

### Quick Health Check

```bash
# HTTP health endpoint
curl -s http://localhost:6300/health

# Check process is running and responsive
docker exec midnight-proof-server ps aux | grep proof-server

# Check recent logs for errors
docker logs midnight-proof-server --since 10m | grep -i "error\|fail\|exception\|oom"
```

### Comprehensive Health Check Script

```bash
#!/bin/bash
# save as: check-proof-server.sh

echo "=== Proof Server Health Check ==="

# 1. Container status
CONTAINER_STATUS=$(docker inspect midnight-proof-server --format='{{.State.Status}}')
echo "[1/5] Container status: $CONTAINER_STATUS"

# 2. Health endpoint
HTTP_CODE=$(curl -s -o /dev/null -w "%{http_code}" http://localhost:6300/health)
echo "[2/5] Health endpoint: $HTTP_CODE"

# 3. Memory usage
MEM_USAGE=$(docker stats midnight-proof-server --no-stream --format '{{.MemPerc}}')
echo "[3/5] Memory usage: $MEM_USAGE"

# 4. Uptime
UPTIME=$(docker inspect midnight-proof-server --format='{{.State.StartedAt}}')
echo "[4/5] Started at: $UPTIME"

# 5. Recent errors
ERROR_COUNT=$(docker logs midnight-proof-server --since 30m 2>/dev/null | grep -ci "error\|fail" || echo "0")
echo "[5/5] Errors (last 30m): $ERROR_COUNT"

# Overall verdict
if [ "$CONTAINER_STATUS" = "running" ] && [ "$HTTP_CODE" = "200" ]; then
    echo -e "\n✅ Proof server is healthy"
else
    echo -e "\n❌ Proof server needs attention"
fi
```

### Integrating with Monitoring

For production setups, add proof server health checks to your monitoring:


## Prevention Checklist

| Check | Frequency | Command |
|-------|-----------|---------|
| Version match with node | Weekly | Compare proof-server and node versions |
| Disk space for params | Weekly | `df -h /var/lib/docker` |
| Memory headroom | Weekly | `docker stats --no-stream` |
| Health endpoint | Daily | `curl http://localhost:6300/health` |
| Error log review | Daily | `docker logs --since 24h | grep -i error` |

## Conclusion

Most proof server failures fall into one of five categories: server not running, first-time parameter download, wire format mismatch, version incompatibility, or memory exhaustion. Each has a clear diagnostic path and a specific fix.

The single most important rule: **keep your proof server version exactly matched to your Midnight node version**. If you upgrade one, upgrade both.
